guide / security

Security and data changes

Identify protected assets, actors, trust boundaries and concrete abuse/failure cases. Verify server-side authorization and tenant isolation; validate inputs at boundaries. Use established security libraries and repository controls. Keep secrets outside tracked code, fixtures, reports and logs.

Choose protections from the actual threat model/platform. Review credentials, dependency provenance/updates, transport/storage protections, retention and least privilege where affected. Human-facing errors follow both product languages; machine codes remain stable.

Logs/telemetry use minimal information. Technical IDs can still be sensitive: redact, pseudonymize or omit according to policy. Verify error/debug paths as well as success paths. Use synthetic or suitably anonymized test data.

For schema/persistent-format changes, specify old/new compatibility, ordering, idempotency and interrupted execution. Test representative migrations, backup restoration and chosen rollback/forward recovery on a safe copy. Do not claim recovery without a restoration check. Destructive production recovery needs an explicit scoped mandate.

For APIs/jobs, test unauthorized access, malformed inputs, timeouts and safe retries as relevant. For dependency/native-runtime changes, verify versions and behavior actually packaged. Track unresolved vulnerabilities with impact, owner and remediation or accepted exception.

Put project-specific constraints in profile, lasting tradeoffs in decisions, and security evidence in the relevant work/release record.
