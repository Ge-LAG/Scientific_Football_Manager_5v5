Language and localization

SurfaceDefault
Method, agent instructions, coordination with RobertsonEnglish.
Private working languageEnglish requested; no reasoning transcript. This is not an observable acceptance gate.

End-user reports, guides and explanatory deliverablesFrench. Add English when part of the bilingual product or requested.

Human explanatory prose embedded in codeFrench for new comments/explanations by default; preserve conventions required for interoperability.

Centralize product strings in the stack's localization mechanism. Use stable keys, complete sentences and named parameters; avoid sentence fragments assembled in code. Cover plurals, empty states, errors, accessibility labels and exports. No hard-coded UI strings in either language.

Provide an accessible language selector and persist the explicit choice in the appropriate setting. Without a saved choice, use French even on an English browser/system. Missing or unsupported locales fall back to French. Define dates, numbers, currencies and timezones in the profile; language must not silently change stored values.

For affected surfaces, verify catalog keys and parameters in both languages, absence of raw keys, first-use French default, switching across reload/restart, layout, accents, plurals and accessible names. Exercise the touched French and English flows with realistic text lengths.

Set each authored HTML record’s lang attribute to its actual prose language (fr or en), including PO test sheets created from English templates.

The method remains English. Record local language overrides only when the product request calls for a different policy.
