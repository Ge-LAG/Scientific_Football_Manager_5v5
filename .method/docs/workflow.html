guide / workflow

Work in verifiable increments

  1. Locate. Read context; verify repository, branch and existing changes. Retrieve relevant contracts, code and decisions.
  2. Frame. A small correction can keep intent and acceptance in the task. A significant lot gets one work record: outcome, acceptance, scope, dependencies, risk and owner.
  3. Implement. Follow existing architecture and stack conventions. Resolve routine choices autonomously; record lasting tradeoffs. Split when a lot no longer has an independently verifiable result.
  4. Verify. Use risk-based checks and inspect the final diff. Rerun invalidated checks after changes; do not repeat unchanged expensive checks without reason.
  5. Close or hand off. Record outcome, evidence, unresolved items and next action. Update project.json only when current facts/pointers change; increment revision/date. Publish shared documentary edits through guarded replace. Validate before integration/release.

States: draft → ready → active → review → accepted → released, when release applies. Use blocked for a specific dependency and name the resumption state; archived is closed history. Accepted requires applicable evidence, including product acceptance when designated. Unavailable checks leave review/blocked, never an invented waiver. Documentation fixes need no release stage.

Commit code and corresponding work evidence coherently when committing is within scope. A dirty worktree may be handed off for review: record its actual state and preserve user changes. Never fabricate a hash or force a documentation commit for a session ritual.

After interruption/compaction, read state and work, then verify changed code facts. Historical evidence applies to its recorded revision. Checkpoint after a meaningful result, focus change, blocker or handoff; not every tool call. Do not repeatedly summarize full sessions.

Closure fields and evidence bindings follow evidence; normal markup alone cannot prove acceptance.
